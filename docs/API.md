# API Overview

Full interactive documentation (request/response schemas, try-it-out) is auto-generated by
FastAPI and served at `/docs` (Swagger UI) and `/redoc` whenever the API is running. This page is
a map of the surface area, not a substitute for it.

Base path: `/api/v1` (versioned so a future `/api/v2` can be introduced without breaking existing
consumers — see `configs/settings.py::api_v1_prefix`).

All endpoints except `/health`, `/auth/register`, and `/auth/login` require a JWT bearer token
(`Authorization: Bearer <token>`) obtained from `/auth/login`. Roles are ordinal:
`viewer < loan_officer < risk_analyst < admin`; each endpoint requires a minimum role.

## Auth (`/auth`)

| Method | Path | Min role | Purpose |
|---|---|---|---|
| POST | `/auth/register` | none | Create a user |
| POST | `/auth/login` | none | Get access + refresh tokens |
| POST | `/auth/refresh` | none (valid refresh token) | Rotate an access token |
| GET | `/auth/me` | any authenticated user | The caller's own profile (id, username, email, role) |

## Scoring (`/predict`)

| Method | Path | Min role | Purpose |
|---|---|---|---|
| POST | `/predict` | loan_officer | Score a single application |
| POST | `/predict/batch` | loan_officer | Score a batch synchronously |
| POST | `/predict/batch/async` | loan_officer | Queue a large batch as a background job |
| GET | `/predict/batch/status/{job_id}` | loan_officer | Poll an async batch job |
| GET | `/predict/history` | loan_officer | Query prediction history (customer_id filter, limit) |

A `/predict` response carries the calibrated `predicted_probability`, scorecard
`credit_score` points (600 = 50:1 good:bad odds, +20 doubles the odds), `risk_band`,
`decision` and `decision_threshold`. For a **declined** application,
`adverse_action_reasons` lists up to four ECOA / Reg B principal reasons, strongest first:

```json
"adverse_action_reasons": [
  {"rank": 1, "code": "R02", "reason": "Proportion of revolving balances to credit limits is too high",
   "contribution": 0.41, "features": ["revolving_utilization", "utilization_x_low_score"]},
  {"rank": 2, "code": "R05", "reason": "Delinquency on past or present credit obligations",
   "contribution": 0.22, "features": ["num_delinquencies_2yrs", "has_recent_delinquency"]}
]
```

The reason codes are also written to the audit log entry for that prediction. Age,
marital status and state are accepted (for fair-lending monitoring) but never reach the
model, so changing them cannot change the decision.

## Admin (`/admin`) — new

All routes require the `admin` role (enforced once at the router level via `dependencies=[...]`,
not repeated per-handler). Listing endpoints return a paginated `{items, page, size, total,
total_pages}` envelope (`core/pagination.py::Page`), driven by `?page=&size=&sort_by=&sort_order=`
query params.

| Method | Path | Purpose |
|---|---|---|
| GET | `/admin/users` | Paginated user list |
| GET | `/admin/users/{user_id}` | Single user detail (includes lockout state) |
| PATCH | `/admin/users/{user_id}/status` | Activate/deactivate a user (can't deactivate yourself) |
| PATCH | `/admin/users/{user_id}/role` | Change a user's role (can't remove your own admin role) |
| POST | `/admin/users/{user_id}/unlock` | Clear a lockout (see Account lockout below) |
| GET | `/admin/audit-logs` | Paginated, filterable (`user_id`, `action`) audit-log query |

Before this pass, `AuditLog` rows were written on every login/predict/promote/rollback but nothing
ever read them back out — `/admin/audit-logs` closes that gap.

## Health (`/health`) — expanded

The original bare `GET /health` (root, no `/api/v1` prefix) is unchanged — it's still what
`deployment/kubernetes/*.yaml` and both Dockerfiles' `HEALTHCHECK` directives point at. Everything
under `/health/...` is new and additive, also mounted at root (unversioned -- an infra probe
shouldn't need to track API version bumps):

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | (unchanged) liveness + current champion version |
| GET | `/health/liveness` | Always `200` if the process can handle a request at all (no I/O) |
| GET | `/health/readiness` | `503` if the DB or champion model isn't available (k8s readiness probe) |
| GET | `/health/database` | DB connectivity check in isolation |
| GET | `/health/model` | Champion-model-loaded check in isolation |
| GET | `/health/version` | App name, version, environment, Python version |
| GET | `/health/system` | Process uptime, platform info |

## Account lockout

`POST /auth/login` locks an account for 15 minutes after 5 consecutive failed attempts
(`core/constants.py::MAX_FAILED_LOGIN_ATTEMPTS` / `ACCOUNT_LOCKOUT_MINUTES`). A locked account
returns `401` with `AccountLockedError`'s message (a subtype of `AuthenticationError`, so no new
exception handler was needed) even if the correct password is supplied. An admin can clear the
lockout early via `POST /admin/users/{user_id}/unlock`.

## Correlation IDs and security headers

Every response carries an `X-Correlation-ID` header — echoing a caller-supplied one, or a
server-generated UUID4 if absent — and every log line emitted anywhere during that request
(router, service, repository, background task) is automatically tagged with the same ID via
`core/logging.py::CorrelationIdFilter`. Every response also carries `X-Content-Type-Options`,
`X-Frame-Options`, `Referrer-Policy`, and `Permissions-Policy` (plus `Strict-Transport-Security`
outside debug mode). See `api/middleware.py`.

## Errors

Validation errors return `422` with a Pydantic-generated detail body. Authentication failures
(including `AccountLockedError`) return `401`; authorization (role) failures return `403`; unknown
model versions, unknown users, and similar domain errors return `404`; duplicate-resource errors
return `409`; other domain errors return `400` via the platform's typed exception handlers
(`core/exceptions.py` -> `api/app.py` exception handlers). Rate limiting (`slowapi`, default
60 requests/minute/IP globally, configurable via `RATE_LIMIT_PER_MINUTE`; `/auth/login` and
`/predict/batch` additionally apply stricter per-route limits, see `core/rate_limit.py`) returns
`429`.

## Data quality (`/data-quality`, `/reports/data-quality`)

Validation + profiling + a composite 0-100 quality score against the reference dataset
(`data/raw/credit_applications.csv`), persisted as history. `risk_analyst` role required for all
four endpoints below.

| Method | Path | Purpose |
|---|---|---|
| POST | `/data-quality/run` | Runs validation + profiling + scoring, persists a new report row |
| GET | `/data-quality/latest` | Most recent persisted report (`404` if none has been run yet) |
| GET | `/data-quality/history` | Paginated report history (`?page=&size=&sort_by=&sort_order=`) |
| GET | `/reports/data-quality` | Downloadable HTML rendering of the *latest* persisted report |

`GET /reports/data-quality` deliberately does not trigger a fresh check itself (that's what
`POST /data-quality/run` is for) — a `GET` a browser tab or crawler could hit accidentally
shouldn't have a side effect that writes a new database row.

## Security & RBAC updates (this pass)

The role model described at the top of this document (`viewer < loan_officer < risk_analyst < admin`) is the **ordinal** subset. Two more roles exist as of this pass — `super_admin` (above `admin`) and two **lateral** roles, `auditor` and `ml_engineer`, that sit outside the ordinal ladder entirely (broad-but-narrow permissions that don't fit "somewhere on the tier list" — see `docs/SECURITY.md` §2.1 for the full rationale). The authorization matrix in `docs/SECURITY.md` §2.2 is the authoritative reference; the tables above in this document predate the lateral-role expansion and should be read as "ordinal minimum" only.

Notable corrections to the tables above:
- `GET /models/versions` and `GET /models/comparison` now require only `viewer` (previously listed as `risk_analyst`, and before this pass had **no auth dependency at all** — a fixed security bug, see `docs/SECURITY.md` §2.3).
- `POST /models/promote`, `/rollback`, `/reload-cache` admit `admin`+ **or** `ml_engineer`, not `admin` alone.
- `GET /admin/audit-logs` admits `admin`+ **or** `auditor`; every other `/admin/*` route remains `admin`+ only (the router no longer applies one blanket router-level dependency — each route now sets its own).
- `POST /data-quality/run` and `GET /reports/*` (model comparison, evaluation, drift, performance, data-quality) admit `risk_analyst`+ **or** the relevant lateral role(s) — see `docs/SECURITY.md` §2.2 for the exact list per endpoint.

### New: admin-issued user creation

| Method | Path | Min role | Purpose |
|---|---|---|---|
| POST | `/admin/users` | admin | Create a user with ANY of the 7 roles (`AdminUserCreate` schema) — the only way to create a privileged account over HTTP; see `docs/SECURITY.md` §1.4 |

`POST /auth/register` (public, no auth) now only accepts `role: "viewer"` or `role: "loan_officer"` — any other value is rejected with `422` before it reaches business logic.

### New: MFA (`/auth/mfa`)

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/auth/mfa/enroll` | Bearer token | Generate a TOTP secret + provisioning URI for the authenticated user |
| POST | `/auth/mfa/confirm` | Bearer token | Verify a TOTP code against the enrolled secret; flips `mfa_enabled=true` and returns backup codes on success |
| POST | `/auth/mfa/disable` | Bearer token + current password + (TOTP code or backup code) | Disable MFA for the authenticated user |
| POST | `/auth/mfa/verify-login` | `mfa_challenge_token` (from a `POST /auth/login` response with `mfa_required: true`) + (TOTP code or backup code) | Completes login for an MFA-enabled account, returns real access/refresh tokens |

`POST /auth/login`'s response shape changed: it now returns `{"mfa_required": false, "access_token": "...", "refresh_token": "..."}` for a non-MFA account, or `{"mfa_required": true, "mfa_challenge_token": "..."}` for an MFA-enabled one (no tokens yet). See `docs/SECURITY.md` §1.3.

### Refresh token rotation

`POST /auth/refresh` refresh tokens are now single-use (rotation via `User.token_version`) — see `docs/SECURITY.md` §1.2. Reusing an already-consumed refresh token now correctly returns `401`, not a second valid token pair.

### Response headers

Every response now also carries a `Content-Security-Policy` header (relevant since `/reports/*` serves raw HTML a browser renders directly) and `/auth/*` responses carry `Cache-Control: no-store`. See `docs/SECURITY.md` §3.

## AI Copilot (`/copilot`) — new

Deterministic, template-based narrative generation over the platform's existing
structured data (SHAP/counterfactual explanations, evaluation metrics, monitoring
stats, data-quality scores) — no external LLM API call, no API key to provision. See
`explainability/copilot.py`'s module docstring for the full rationale and
`docs/ROADMAP.md` for a real LLM-backed conversational mode as a possible future,
additive enhancement.

Every endpoint returns the same shape: `{"headline": str, "narrative": str, "insights":
list[str], "recommended_actions": list[str]}`.

| Method | Path | Min role | Purpose |
|---|---|---|---|
| POST | `/copilot/explain-prediction` | loan_officer | Plain-English explanation of a single prediction + recommended actions, reusing the same SHAP/counterfactual computation as `/explain` and `/reports/explainability` |
| GET | `/copilot/summary/model-performance` | risk_analyst (or auditor/ml_engineer) | Narrative summary of the champion model's latest evaluation metrics |
| GET | `/copilot/summary/monitoring` | risk_analyst (or auditor/ml_engineer) | Narrative summary of prediction volume, latency, and drift |
| GET | `/copilot/summary/data-quality` | risk_analyst (or auditor/ml_engineer) | Narrative summary of the latest data-quality report (`404` if none has been run yet) |
| GET | `/copilot/executive-briefing` | risk_analyst (or auditor/ml_engineer) | Combines all three summaries above into one briefing; degrades gracefully if a section's data isn't available yet |

## Business Rule Engine (`/rules`)

Admin/risk-analyst-editable approval, rejection, and manual-review rules. Conditions
are a closed JSON grammar (`{"field", "operator", "value"}`, composed via
`{"all": [...]}` / `{"any": [...]}`) — never a free-text expression evaluated at
runtime. See `rules/engine.py`.

| Method | Path | Min role | Purpose |
|---|---|---|---|
| POST | `/rules` | risk_analyst | Create a rule |
| GET | `/rules` | risk_analyst (or auditor/ml_engineer) | List rules, optional `?rule_type=` filter |
| GET | `/rules/{rule_id}` | risk_analyst (or auditor/ml_engineer) | Get a single rule |
| PUT | `/rules/{rule_id}` | risk_analyst | Update a rule (bumps `version`, snapshots prior state to the audit log) |
| POST | `/rules/{rule_id}/activate` | risk_analyst | Reactivate a rule |
| POST | `/rules/{rule_id}/deactivate` | risk_analyst | Deactivate a rule |
| POST | `/rules/simulate` | risk_analyst | Dry-run rules against a batch of hypothetical contexts, no persistence |

band), backed by a single `SystemConfig` table with built-in defaults. See
`services/config_service.py`.

| Method | Path | Min role | Purpose |
|---|---|---|---|
| GET | `/config` | risk_analyst (or auditor/ml_engineer) | List all config keys (persisted overrides + still-at-default), optional `?category=` filter |
| GET | `/config/{key}` | risk_analyst (or auditor/ml_engineer) | Get one key's current value (falls back to its default) |
| PUT | `/config/{key}` | admin | Set/override a config value — these keys directly control automated decisioning behavior |
